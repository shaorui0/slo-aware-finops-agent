# c0033 核实 K8s 变更是否真的省钱

- 「省钱」只有两种来源：节点少了，或者腾出的容量吸收了本来要新开节点的增长。所以账单只看节点小时，节点数每小时对 requests 做一次 FFD，不手填。
- packing-trap 是最好的演示：request 降了，账面释放 $36.91，账单一分没变。可兑现与账面释放要分开报，核实这一步把它坐实了。
- 反直觉：装箱不可加。api-steady 和 no-slo 各自单独都能省一台，合起来不一定是两台。单条归因只能约定顺序，每条算它加入时多空出的节点；总账不受影响。
- 精确闭合靠状态链：相邻两环只差一件事，差额相加自动等于总变化。我先试了 Shapley 平均，结果每条都分到一点，没人能读，换回按应用顺序归集。
- 「实际」取控制组校正后的值（无关增长扣掉），和附录口径一致；账单的朴素差另列。无关增长吃掉了一半节省，两个数都要给。
- 预测为 0 的计划实现率无法定义。agent 在决策里就说了节点数不变，核实的意义是确认没有意外，不是凑一个百分比。
- 搜场景参数时发现：四条 cpu 变更挤在同一个 cpu 吃紧的集群里，packing-trap 在大多数增长设定下都会变成「决定性的那一条」，实际不为 0。想让它稳定为 0，要么没有需要新节点的增长，要么它排在前面。这本身就是局限，写进了文档。
- 场景事件（set_request、rollback、scale）放在覆盖层的 add_events 里，metrics_server 忽略，不改 k8s_world.py；代价是指标服务暂时不吐出变更后的 requests，生产适配器要改读 requests 历史。
