# c0034-k8s-loop 笔记

- 各个部件分别能跑，不等于一条线能跑。接环第一天就暴露了三处「猜的形状」：报告读的台账字段是 `state`，真实的是 `status`；考卷分数里没有逐条 `items`；叙述从一段字符串变成了对象。契约写在文档里，不如让真实输出去喂下游。
- 执行器必须回写台账，否则台账只会停在 proposed。规则很短：过了闸门开始改 → approved → applied；观察通过 → verified；停止条件命中并核对回滚 → rolled_back；refused 什么都不动；回滚没恢复就停在 applied，交给人。台账写失败不改执行结果，只在记录里说明，因为「改了集群」比「记了账」更重要，不能反过来让记账失败吞掉事实。
- 生成的计划一次只改一种资源，旧的漂移闸门把整个 requests/limits 全比一遍，会把「另一种资源不同」误判成漂移。闸门只该比较计划涉及的东西。
- 反直觉：降 request 不会让延迟变差，更不会 throttle。throttle 来自 limit。所以 demo 里 throttle 这个停止条件根本没被测到。能触发回滚的是 p99，而在空闲机器上它也要靠注入过载才会动。写下来，不把它说成因果：这个演示证明的是守卫会在退化时触发并回滚，不是降 request 导致了退化。
- 一个坑：第一次 demo 两条计划都走了 verified，没有回滚。原因是压测打满了 pod，但 app 的 p99 只量「处理线程开始之后」的时间，接不进去的连接堵在内核 backlog 里，p99 一直 0.07 秒。改成单 worker、延迟从排队前开始计，过载才如实出现在 p99 上。压测数字看着很高，不等于被测指标会动。
- 证据标签不能加在证据条目里：条目会进叙述的提示词，cassette 以提示词为键，加一个字段 18 条 cassette 全部失效。展示用的人话标签放在渲染层，按查询语句和窗口推导。
- demo 用生成的计划，就得让 demo 集群等于计划假设的世界（3 副本、容器名 app、cpu 1/2、memory 2Gi/3Gi），而不是反过来把计划改成适应集群。只在两者真的不同时才改写 `before`，并且大声打印。一条单测守住这个等式。
- 两条计划（cpu、memory）各自走一条路：一条在过载下回滚，一条在正常负载下 verified。回滚是终态，同一提案不能再走 verified，所以 demo 需要两个提案才能同时展示两条台账路径。
- 样例报告里的「核实结果」仍是手写夹具（t6 的真实核实文件不在本分支）。夹具每行带 `note`，报告把「手写夹具」显示出来，不让样例冒充真实核实。
