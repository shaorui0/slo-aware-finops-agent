c0034-k8s-loop：把执行、台账、流水线、报告接成一条线

改了什么

缺口 改动
执行不更新台账 act.py 每个结局后回写 runs/k8s_state.json：proposed → approved → applied → verified 或 rolled_back；refused 不动；failed 停在 applied
流水线不出报告 k8s run 同时写 k8s_daily.html、k8s_weekly.html、k8s_monthly.html；新增 --prev-run、--score；新增 k8s ledger 打印台账
报告读的是猜的形状 台账读 status；考卷读 k8s_eval.json；计划是 {run_id, as_of, safe_halt, plans[]}；叙述是对象，在「结论」里标「由模型撰写、数字已核对」，would_change 显示为「什么情况下判定会变」
报告打磨 证据表带「含义」列（E8 有效天数、E9 覆盖率）；无值、无关的证据行不显示；「做完应该是什么样」第一句说钱动不动、为什么
demo 用手写计划 demo 用 k8s run 对合成世界生成的计划，demo 清单与世界里的 api-steady 一致；展示拒绝、回滚、verified、台账流转，最后渲染含真实 actions 的周报
样例报告是夹具 样例由真实运行生成（day1/day2、真实台账、真实 demo actions、k8s-eval 的考卷）

人工 gate 与回滚

改集群的唯一入口仍是 act.py：审批文件由人创建；上下文只能是 k3d-finops-test；漂移就拒绝；停止条件命中自动回滚。台账只记录结局，不触发动作。回滚本 change 即 revert 这几个 commit。

停止条件的诚实边界

计划只降 request，CFS throttle 由 limit 决定，所以 throttle 条件在 demo 里没有被测到。回滚由 p99_seconds > SLO 触发，靠观察期内注入过载；它证明守卫在退化时会触发并回滚到变更前，不证明降 request 导致了退化。

证据 6. 停止条件：诚实的边界

  • 计划只降 request。CFS throttle 由 limit 决定，demo 里 throttle_ratio 全程 0，所以 throttle 这个停止条件没有被测到，计划里保留它。
  • 回滚由 p99_seconds > 0.3 触发（SLO 目录里 api-steady 的 p99 目标）。在空闲机器上，单独降 request 并不会让延迟变差；demo 的回滚路径靠的是观察期内注入过载（2 个压测器 × 200 rps），证明的是「守卫在退化时触发并回滚到变更前」，不是「降 request 导致退化」。
  • 为了让过载如实反映在 p99 上，ops/k3d/app.py 改成单 worker（一次处理一个请求，其他的在锁上排队，延迟从排队前开始计）。之前的版本在 GIL 下接不进去的连接堵在内核 backlog 里，p99 在 saturation 下也只有 0.07 秒。第一次 demo（尚未改 app）两条计划都走了 verified，没有触发回滚，这就是改 app 的原因。
