0033-k8s-verify

c0033 K8s 节省核实

做了什么

主线之前只回答「该改什么」。这次回答「改了之后账单真的降了吗」。核实器 finops_agent/k8s/verify.py 比较 BEFORE 与 AFTER 两个 7 天窗口的节点小时账单，把账单变化精确分解为五类原因，再逐条给出预测、实际、实现率和偏差原因。

  • 每个小时的节点数不是手填的，是对当小时全部 pod 的 requests 做 first-fit decreasing（和决策里算「可兑现」是同一个函数）。HPA 副本数由世界生成的用量按公式推出。
  • 场景覆盖层 after_apply.yaml（四条计划加一次无关增长）与 after_clean.yaml（对照）在基础世界上加带时间的事件，不改 k8s_world.yaml。
  • make k8s-verify 产出 runs/k8s-verify/k8s_verify.json（c0032 契约形状）并重新生成 docs/K8S_SAVINGS_VERIFICATION.md。

结果

变更 预测 $/月 实际 $/月 实现率 偏差原因
api-steady cpu 1 到 0.25 140.16 140.16 100% 无
packing-trap cpu 1 到 0.2 0 0 无法定义 (e) 装箱没兑现，账面释放 36.91 没进账单
hpa-managed cpu 1 到 0.45 0 0 无法定义 (b) +70.08 与 (c) -70.08 抵消
no-slo cpu 1 到 0.2（被回滚） 140.16 0 0% (b) -70.08，(d) -70.08

账单从 $840.96 变到 $770.88，变化 -$70.08/月。控制组校正后的实际合计 $140.16，预测合计 $280.32，实现率 50%。两个「实际」不同：无关增长让账单多了 $70.08，吃掉了一半节省。

闭合：各原因之和 -70.08，账单变化 -70.08，差 4e-14。所有应用顺序下都闭合（单测遍历 24 种）。

验收

见 openspec/changes/c0033-k8s-verify/evidence.md：make k8s-verify 输出、单测 30 项、全量 316 + 71 项、check_rules --docs 通过、make k8s-eval 18/18 指标与改动前一致、k8s_world.yaml 无改动。

取舍与局限

  • 预测取决策的 realizable_usd_month。packing-trap 与 hpa-managed 单独应用本来就预测 0，所以它们的实现率无法定义。核实的价值是确认账单没有意外。
  • 装箱不可加，单条归因按应用顺序。换顺序单条数字会变，总数不变。
  • HPA 模型没有容忍带与稳定窗口；合成指标不随 request 变化，slo_ok 只反映世界自带的 SLO 信号。
