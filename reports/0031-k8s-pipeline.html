0031-k8s-pipeline

c0031 K8s 主线串联

结论

  • 主线接通：SLO 目录（第三输入）→ collect → decide → 隔离 LLM 叙述 → 提案台账 → 计划 → k8s_decisions.json。
  • make k8s-eval 对世界的 expect 打分：18/18 判对，unsafe_allow 0，unknown_recall 1.0，request_in_range 1.0，realizable_accuracy 1.0。已进 CI，回放盒带，缺盒带即失败。
  • make k8s-days 三天连续运行：第 2 天 8 条 unchanged、2 条 expired；第 3 天漂移的 api-steady cpu 提案过期并以新目标重提。
  • 附录 make eval 数字不变。

改了什么，为什么

部分 内容
SLO 目录 testenv/k8s_slos.yaml：每个 (namespace, workload) 的 availability、p99_seconds 目标与批任务 deadline_seconds。没有 SLO 的 workload 不在目录里。testenv/test_k8s_slos.py 断言与世界的 slo 块一致
collect、policy 目标与 deadline 取自目录（证据 source: slo_catalog）；燃烧率与剩余预算仍取自指标；workload 不在目录里则条件 C 为 UNKNOWN，即使有 slo_* 指标；决策追加 container、slo
条件 D 以 nodes.max 作 max_nodes，自动扩缩能为回滚补节点；未知则保持字面行为。契约文字在 spec delta 里修订
narrate 每条决策一次隔离调用；数字过 judge/validate.py 落地，含未取自证据数字的句子抹除；声称其他 verdict 的句子也抹除；verdict 不变断言；失败退回模板；全部调用进 trace
plans ALLOW 与 REQUIRE_APPROVAL 出契约形状的计划；停止条件由决策与 SLO 推出
ledger runs/k8s_state.json：5% 去重、verdict 或目标变化则 expired、applied 后 SLO 退化则 halted 并 safe_halt
评估 eval/score_k8s.py：五个指标、硬闸、叙述数字落地检查、基线回归

K4 叙述

  • 18 条全部来自真实 claude -p（sonnet）录制的盒带：回放 trace 为 148381 输入 token、9920 输出 token、录制成本 0.6927 USD。
  • 评分对每条叙述重跑数字落地检查，未取自证据的数字为 0。
  • 1 条第一次返回的 JSON 嵌套错位，被严格解析拒绝；按设计 record 模式下该条退回模板；删除该盒带重录后合格。
