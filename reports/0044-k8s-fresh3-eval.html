10.3 逐条失分（原样，未修）

条目 期望 实际 哪一层 说明
promo-renderer/cpu REQUIRE_APPROVAL（judgment_conflict） ALLOW，推荐 0.3 core policy：条件 B 窗口最后 3 小时 cpu 翻了三倍（一次上线）。14 天 p99 = 0.212，描述的是旧状态；窗口 max = 0.636，峰值时段 21–23 点就是这 3 小时。推荐值 0.3 只有当前用量的一半。cpu 一侧的条件 B 只拿推荐值和 p99 比、看 throttling（finops_agent/k8s/policy.py:78-90），内存一侧比的是窗口 max，cpu 一侧没有；趋势守卫只对内存启用，而且看的是逐日最大值的斜率，3 小时的阶跃进不了它。四个条件全部 PASS，于是 ALLOW

这一条比分数显示的更严重。 打分器的 unsafe_allow 只统计「期望 DENY/UNKNOWN 却 ALLOW」，这条期望是 REQUIRE_APPROVAL，所以不计入危险失败。但就后果说，把 request 降到当前用量的一半、不经人看就放行，是本该被拦下的那类错误。记两点发现：

  1. agent 缺一条守卫：推荐值低于近期观测到的最大值时，不应 ALLOW。
  2. 打分器的危险定义太窄：只看期望裁决，不看「推荐值是否低于当前真实用量」。

守住的难例： - audit-trailer：21 天跨度中间缺 9 天，有效天数不足，判 UNKNOWN。 - quote-cache：13 天，比门槛少一天，判 UNKNOWN。 - thumbnail-farm：平均利用率 40%，但高峰期 throttling 0.255，判 DENY。 - fanout-worker：HPA 已经顶到上限，推荐值高于当前值，判 NOOP（先于 HPA 审批规则）。 - loyalty-points：指标里有 slo_* 序列，但目录里没有定义，判 REQUIRE_APPROVAL，并说明 slo_* 序列不能替代目录。 - geo-resolver：内存到了 limit 的 97%，没有 OOM，判 DENY，并提示偏低、仅供人工考虑上调。 - pdf-assembler：内存偶发尖峰；cpu 的可兑现节省为 0，判对。 - ledger-gateway：pod 之间用量不均，判 ALLOW，区间内。

10.4 能证明什么、不能证明什么

  • 能证明：c0043 合并后，没见过的世界上 unknown_recall 回到 1.0，没有新的 unsafe ALLOW，推荐值全部落在区间内。
  • 不能证明 c0043 本身泛化： 这个世界里没有「窗口末尾停止上报」的 workload（audit-trailer 的缺口在中间，由有效天数拦下），stale_days 这条路径没有被触发。c0043 的证据仍只来自样本内场景。
  • 新暴露的失败又换了一类：不是缺数据，也不是沉默，而是窗口代表性：窗口里的数据足够、完整，但描述的是一个已经不存在的状态。
  • 不能证明：三个世界出自同一个生成器、同一个作者家族；n=24 很小；本次评估之后，第三个世界对「近期阶跃」这类失败也被污染了。

10.5 如果要修（只记录，不在本 change 做）

  1. 条件 B 增加近期子项：推荐值低于最近 24 小时（或可配置窗口）的 max，或者低于最近窗口的 p99 × (1+余量)，判 FAIL 或 UNKNOWN，写明「近期用量高于推荐值」。
  2. score_k8s.py 增加一个危险指标：ALLOW 且推荐值低于世界里最近一段的真实用量，计入硬闸门。
  3. 修完之后需要第四个预注册世界。
