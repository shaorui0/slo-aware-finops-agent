c0046-k8s-recent-regime：近期阶跃不能再被 ALLOW

改了什么

  1. 条件 B 增加「近期用量」子项（CPU、内存都适用）：最近 recent_hours（默认 6）小时内的观测最大值 × (1+margin) 高于推荐值，则 B = UNKNOWN，verdict = REQUIRE_APPROVAL。
  2. 新增证据条目（查询 + 窗口 + 值），日报里有中文标签「近期使用量 max（最近 N 小时内的最大值）」。只在子项构成因素时写入，其余决策与 LLM 提示不变，盒带没有重录。
  3. 打分器新增硬闸门 allow_below_recent：ALLOW 且推荐值低于世界里的真实近期用量。近期用量由打分器从世界文件重新生成，不读 agent 的数字，不依赖 expect。
  4. 样本内用例 testenv/k8s_scenarios/recent_step.yaml：CPU 最后 3 小时翻三倍。

为什么

EXPERIMENTS §10：第三个预注册世界里 promo-renderer 的 CPU 在最后 3 小时翻了三倍，推荐值 0.3 core 只有当前用量的一半，verdict 却是 ALLOW。CPU 一侧的条件 B 只比 p99、看 throttling；趋势守卫只管内存且看逐日峰值。旧打分器的 unsafe_allow 只看期望裁决，这条期望是 REQUIRE_APPROVAL，所以这次危险放行没有计入任何指标。

两个判断

  • UNKNOWN 而不是 FAIL。 几小时的数据分不出「新常态」和「一次性尖峰」。FAIL 等于替人判了；UNKNOWN 落到 REQUIRE_APPROVAL，人带着近期证据决定。证据明确（throttling、OOM）才 FAIL。
  • REQUIRE_APPROVAL 不计入 allow_below_recent。 它前面有人工闸门，该指标衡量的是不经人看就放行的错误；它只作为信息项 approval_below_recent 报告。

污染声明与限制

  • recent_hours = 6 是读过 §10 之后判断出来的，没有对第三个世界扫描或调参。用新打分器给 c0044 当时的决策重新打分，allow_below_recent = 1（promo-renderer/cpu）；用修复后的 agent 重跑该世界，该条为 REQUIRE_APPROVAL。这两个数字都已污染，不是修复的证据；检验泛化需要第四个预注册世界。
  • 6 小时到约 3.4 天前的阶跃，这个子项抓不到。
  • 内存一侧：近期窗口是窗口 max 的子集，真实数据下子项不会触发，只有合成事实的单测覆盖。
